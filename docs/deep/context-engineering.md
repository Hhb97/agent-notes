# 上下文工程深入：预算、压缩与检索优化

> [!ABSTRACT] 一句话版本
> - 上下文窗口是**硬预算**，不是「能塞多少塞多少」：系统提示、历史、工具定义、检索片段、工具结果、输出预留都在抢同一份额度。
> - 压缩的优先顺序是：**工具结果裁剪 → 历史滑窗/摘要 → 状态外置 → 子任务隔离**，而不是先换更贵的模型。
> - 检索质量靠链路优化：查询改写、混合检索、元数据过滤、父子 chunk、重排；**先打印命中片段再调参**。
> - 长任务真正难的是「信息不丢且不爆」，常用做法是把大对象外置到存储、只把摘要与引用放回上下文。

## 一、上下文预算表

| 组成部分 | 谁产生的 | 膨胀原因 | 控制手段 |
| --- | --- | --- | --- |
| 系统提示 / 规则 | 开发者 | 规则越加越多、示例过长 | 精简、分层、把长示例外置 |
| 工具定义（schema） | 框架 | 注册了几十个工具 | 按场景动态挑选工具子集 |
| 会话历史 | 短期记忆 | 多轮累积 | 滑窗、摘要、按相关性取回 |
| 检索片段 | RAG | Top-K 过大、片段过长 | 限 K、限长度、去重 |
| 工具结果 | 工具执行 | 返回整表、整份报文 | 结构化精简、只留必要字段 |
| 中间推理 / 计划 | 循环 | 每轮都把完整计划重发 | 状态外置，只放当前步骤 |
| 输出预留 | 模型 | 未预留导致被截断 | 明确 `max-tokens` 与预算 |

> [!TIP] 先量再调
> 打印一次请求各部分的 token 占比，再决定砍哪里。凭感觉「模型记性不好」就换长上下文模型，往往只是把成本抬高，没解决噪声问题。

## 二、压缩策略对比

| 策略 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| 滑窗 | 只保留最近 N 轮 | 简单、可预测 | 早期约束容易丢 |
| 摘要压缩 | 把较早历史压成一段摘要 | 保留长期意图 | 摘要本身可能丢细节、额外一次调用 |
| 结构化状态外置 | 把事实/计划存数据库，用时取回 | 不占上下文、可审计 | 需要设计数据模型与取回时机 |
| 工具结果裁剪 | 只返回模型需要的字段 | 收益最大、成本最低 | 要在工具层做字段映射 |
| 子任务隔离 | 把重活交给独立上下文的子 Agent，只回传结论 | 主上下文干净 | 增加调用与编排复杂度，见 [多智能体架构与隔离](#/deep/multi-agent) |

**顺序建议**：先裁剪工具结果与检索片段（低风险、收益大），再处理历史，最后才考虑子任务隔离。

## 三、检索链路的优化点

| 环节 | 问题 | 手段 |
| --- | --- | --- |
| 查询 | 用户问法与文档措辞不一致 | 查询改写、多查询扩展、把历史上下文代入改写 |
| 召回 | 纯向量对编号 / 缩写不敏感 | 向量 + 关键词**混合检索** |
| 过滤 | 跨租户、跨权限混检 | 元数据过滤前置（先按权限缩小范围再检索） |
| 切分 | 片段太碎没语义、太大有噪声 | 父子 chunk：小块用于检索、大块用于作答上下文 |
| 排序 | Top-K 里前几条其实不相关 | 重排 rerank，再取少量高质量片段 |
| 拼装 | 片段重复、彼此矛盾 | 去重、按来源标注、提示词要求给出引用 |

> [!WARNING] 权限过滤必须在检索之前
> 若先做向量检索、再在提示词里说「不要看无权内容」，等于已经把敏感片段送进了上下文。正确顺序是**先按当前用户权限过滤候选集，再检索**，见 [企业知识库助手架构](#/deep/case-kb-agent)。

**评测要看链路而不只看答案**：命中率（该找的片段是否进来了）、依据可追溯（答案能否指回片段）、拒答率（资料不足时是否诚实说不知道）。方法见 [可靠性、成本与评测门禁](#/deep/reliability-eval)。

## 四、长任务与上下文隔离

长任务的典型失败不是「模型不够聪明」，而是**中间结果越堆越多，关键约束被挤出去**。常见结构：

- **外置工作记忆**：把文档、代码、表格存到存储 / 文件系统，上下文里只放路径、摘要与当前步骤；
- **显式计划状态**：计划作为结构化状态保存，每轮只注入「下一步」，不重发整份计划；
- **阶段性小结**：每完成一个阶段生成简短结论，替换掉该阶段的原始过程；
- **子任务独立上下文**：把高噪声的探索工作交给子 Agent，主 Agent 只看结论。

## 五、成本与缓存

| 手段 | 说明 |
| --- | --- |
| prompt 缓存 | 系统提示、工具定义这类稳定前缀可复用，减少重复计费（以所用模型服务支持为准） |
| 稳定前缀 | 把不变内容放前面、变动内容放后面，利于缓存命中 |
| 模型分级路由 | 简单分类 / 抽取用小模型，复杂推理才升级，见 [可靠性、成本与评测门禁](#/deep/reliability-eval) |
| 减少轮次 | 工具合并、并行调用、更清晰的终止条件，往往比压缩更省 |

> [!NOTE] 缓存不是正确性保障
> 缓存只影响成本与延迟；若提示词顺序不稳定或版本混杂，命中率会下降。改动系统提示后要重新观察命中与评测结果。

## 常见坑

1. **只看总 token 不看构成**：真正膨胀的往往是工具结果和工具 schema。
2. **摘要压掉关键约束**：把「不得执行写操作」这类硬规则压缩丢了，应把硬规则固定在系统提示层。
3. **Top-K 越大越好**：噪声增多，反而降低答案质量。
4. **把权限过滤放在生成阶段**：敏感内容已进入上下文。
5. **长任务反复重发完整计划**：预算被中间过程吃光。
6. **只看最终答案评检索**：命中错了却归咎于「模型幻觉」。

## 深入追问

> [!QUESTION] 为什么说上下文窗口是「预算」而不是「容量」？
> 因为系统提示、工具定义、历史、检索片段、工具结果、输出预留都要竞争同一额度，且噪声会稀释注意力。需要按优先级装配与裁剪，而不是塞满。

> [!QUESTION] 压缩策略应该按什么顺序做？
> 先裁剪工具结果与检索片段（低风险高收益），再做历史滑窗 / 摘要，最后才引入子任务隔离；每一步都用评测集验证是否丢了关键约束。

> [!QUESTION] 为什么权限过滤必须前置于向量检索？
> 否则无权访问的片段已经被检索进上下文并送给模型，事后靠提示词或护栏无法真正「撤回」这些信息。

> [!QUESTION] 长任务里「结构化状态外置」解决的是什么？
> 把大对象与计划存到外部存储，上下文只保留摘要、引用与当前步骤，避免中间过程挤掉关键约束；同时便于审计与恢复。
