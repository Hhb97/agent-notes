# 可靠性、成本与评测门禁

> [!ABSTRACT] 一句话版本
> - **可靠性 = 失败可分类 + 动作可幂等 + 状态可恢复**；盲目重试只会把失败放大成重复副作用。
> - **成本控制的四个抓手**：预算与轮次上限、模型分级路由、缓存命中、减少不必要的轮次；预算熔断应当是硬开关。
> - **评测要成为发布门禁**：固定用例集（含安全反例）→ 自动跑 → 对比基线 → 越权类指标一票否决 → 灰度 → 线上抽检。
> - 最重要的是把三者串起来：**没有评测，任何「优化」都无法证明是变好**。

## 一、失败分类与处理矩阵

| 失败类型 | 例子 | 是否重试 | 处理 |
| --- | --- | --- | --- |
| 可恢复的瞬时错误 | 网络抖动、限流 429、模型超时 | **是**（退避 + 上限） | 切换备用模型 / 稍后重试 |
| 可修正的语义错误 | 工具参数不合法、字段名写错 | **有限次** | 把精简错误回填让模型自纠正 1～2 次 |
| 不可恢复错误 | 权限拒绝、静态校验拦截、欠费 | **否** | 立即失败并留审计告警 |
| 结果质量问题 | 答非所问、检索命中错误 | **否**（重试无意义） | 降级 / 拒答 / 转人工，进评测集 |
| 状态 / 存储故障 | 检查点写失败 | **否** | 停止推进，避免状态不一致 |

```text
调用 → 分类错误 → 可恢复？→ 退避重试（≤ 上限）→ 仍失败则降级 / 转人工
                → 不可恢复 → 立即结束 + 告警 + 审计留痕
```

> [!CAUTION] 重试前先确认幂等
> 任何写操作（下单、付款、发消息、删除）在重试前必须有**幂等键**或天然幂等语义，否则一次超时重试就是两次副作用。这是 [生产级架构](#/deep/agent-architecture) 里工具执行层的职责。

## 二、恢复与一致性

| 机制 | 解决什么 | 关联 |
| --- | --- | --- |
| 检查点 / 持久化执行 | 长任务崩溃后续跑 | [Python 编排深入](#/deep/python-internals) |
| 幂等键 | 重试不产生重复副作用 | 工具执行层 |
| 补偿动作 | 部分成功后回滚 / 对冲 | 业务流程设计 |
| 统一 run_id | 把模型、工具、检索、审批串成一条链 | 观测与审计 |
| 超时分层 | 模型、工具、整体任务各设不同超时 | 异步长任务不能用 HTTP 超时兜底 |

## 三、成本与延迟

| 手段 | 做法 | 注意 |
| --- | --- | --- |
| **预算与轮次上限** | 单次任务设 token / 时间 / 工具调用数上限，超限熔断 | 必须是硬开关，不是告警 |
| **模型分级路由** | 分类 / 抽取用小模型，复杂推理才升级 | 入口路由先分流，见 [Agent 工作流编排模式](#/deep/agent-workflow) |
| **prompt 缓存** | 稳定前缀（系统提示、工具定义）复用 | 前缀顺序别频繁变，见 [上下文工程深入](#/deep/context-engineering) |
| **减少轮次** | 合并工具、并行无依赖调用、明确终止条件 | 写操作并行要串行化或幂等 |
| **结果裁剪** | 工具与检索结果只留必要字段 | 同时降低噪声 |
| **批处理 / 异步** | 非实时任务错峰执行 | 与 SLA 分开定义 |

> [!TIP] 成本异常往往是行为异常
> 账单突然上涨，通常不是单价变了，而是某个循环没终止、某个工具被反复调用、或多智能体互相转交。先看每步的轮次与工具调用分布，见 [多智能体架构与隔离](#/deep/multi-agent)。

| 层次 | 内容 |
| --- | --- |
| 离线用例集 | 典型问题 + 边界问题 + **安全反例**（越权、危险动作、资料不足、注入文本） |
| 过程指标 | 调用轮次、工具选择、是否多余调用、是否触发预算上限 |
| 结果指标 | 答案正确率、依据可追溯率、拒答正确率 |
| 安全指标 | 越权调用数、未审批写操作、危险语句拦截率、泄漏事件 —— **一票否决** |
| 线上抽检 | 抽样人工复核 + 用户反馈回流用例集 |
| 灰度 | 小流量 → 观察 SLO → 全量；保留快速回滚 |

**基线要存下来**：没有上一版的指标，就无法判断这次改动是回归还是提升。评测用例与结果都应纳入版本管理。

## 五、SLO 与告警

| 指标 | 典型关注 |
| --- | --- |
| 可用性 | 成功返回率、降级触发率 |
| 延迟 | P50 / P95 / P99，区分同步与长任务 |
| 成本 | 单次任务平均 token、预算熔断次数 |
| 质量 | 抽检正确率、拒答率异常波动 |
| 安全 | 越权拦截数、审批拒绝率、注入告警 |
| 可恢复性 | 长任务恢复成功率、检查点写入失败率 |

告警要能定位到 **run_id**；否则「昨晚成本涨了」这类问题很难还原到具体链路。

## 常见坑

1. **所有错误都重试**：权限拒绝、静态校验拦截被反复重试，变成攻击面。
2. **写操作没幂等键**：超时重试造成重复副作用。
3. **预算只做告警不做熔断**：等发现时账单已经失控。
4. **评测集只有正例**：越权与危险动作这类回归全都漏掉。
5. **没有基线**：改完只说「感觉更好」，无法判断回归。
6. **线上坏例不回流**：同类问题反复出现。
7. **SLO 只看平均延迟**：长尾与长任务被平均值掩盖。

## 深入追问

> [!QUESTION] 为什么重试前必须先做错误分类和幂等？
> 因为权限拒绝、校验拦截这类错误重试没有意义，还会放大风险；而写操作若不幂等，一次超时重试就会产生重复副作用。

> [!QUESTION] 为什么安全指标要一票否决，而不是算进总分？
> 越权调用、未审批写操作、敏感信息泄漏属于不可接受事件，不能靠「整体正确率更高」来抵消；只要出现就必须阻断发布。

> [!QUESTION] 成本突然上涨时应该先看什么？
> 先看每次任务的轮次、工具调用分布与委派链，判断是不是循环没终止、工具被反复调用或多智能体互相转交；单价通常不是主因。

> [!QUESTION] 为什么线上抽检发现的坏例要回流用例集？
> 让同类问题变成可自动回归的固定用例，评测闭环才成立；否则每次发布都要靠人工重新发现旧问题。
