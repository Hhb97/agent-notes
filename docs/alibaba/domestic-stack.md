# 国产模型与云平台对照选型

> [!ABSTRACT] 一句话版本
> - 选模型的正确维度不是「榜单分数」，而是**工具调用稳定性、结构化输出可靠性、限流配额、上下文长度、价格结构、能否私有化**。
> - 模型和平台是两件事：**模型决定能力上限，平台决定你能不能稳定、合规、便宜地用上它。**
> - 结论先行：**必须做多模型抽象**（OpenAI 兼容协议 + 网关层适配），不要在任何业务代码里绑死单一厂商 SDK。
> - 国产模型迭代极快，所有具体型号与价格都会过时；本页给的是**评估方法与维度**，请以官方文档为准。

## 一、先分清三层选型

新手常把「选模型」当成一个决定，实际是三个：

| 层 | 决定什么 | 换的成本 |
| --- | --- | --- |
| **模型** | 能力上限、延迟、单价 | 低（改配置），前提是做了抽象 |
| **平台（云厂商）** | 配额、可用性 SLA、知识库/编排能力、账单 | 中（协议可能私有扩展） |
| **部署形态** | 公有云 API / 专属实例 / 私有化 | 高（运维与硬件投入） |

**顺序建议**：先按任务定档位（旗舰/均衡/轻快），再按合规定部署形态，最后按生态定平台。反过来做（先选平台再挑模型）通常会被平台能力绑住。

## 二、国产模型的能力画像

下面的分组是**能力定位**，不是排名——每家都在快速迭代，型号名称几个月就会变。

| 分组 | 代表 | 强项 | 用之前要验的 |
| --- | --- | --- | --- |
| 通用旗舰 | Qwen-Max 系、DeepSeek 旗舰、GLM 高配、Kimi 旗舰 | 复杂推理、长任务、代码 | 单价高，别拿来做分类路由 |
| 均衡/性价比 | Qwen-Plus 系、DeepSeek 通用版、豆包主力档 | 业务主链路 | 工具调用稳定性需实测 |
| 轻快 | Qwen-Flash 系、各家 mini/lite 档 | 分类、抽取、改写、摘要 | 复杂指令遵循弱，别硬压任务 |
| 超长上下文 | 百万级上下文档（Qwen-Flash 长文、Kimi、GLM 长文） | 整仓代码、长文档、会议记录 | 长上下文≠长注意力，中段信息易丢 |
| 多模态 | Qwen-VL、豆包视觉、GLM-V | 文档 OCR、截图理解、视频 | 计费按图/秒算，成本模型不同 |
| 语音 | Qwen-TTS/ASR、豆包语音、讯飞 | 实时对话、转写 | 流式与打断处理是工程活 |

> [!TIP] 一个反直觉的观察
> 在 Agent 系统里，**「便宜模型 + 好工具设计」经常打败「贵模型 + 烂工具」**。因为失败大多来自工具描述含糊、参数设计不合理，而不是模型不够聪明。先按 [工具设计原则](#/tools/tool-design) 把工具打磨一遍，再谈换模型。

三个常见失败类型与对应修法：

| 失败类型 | 表现 | 修法 |
| --- | --- | --- |
| 不调用 | 直接凭记忆回答 | 工具描述写清「什么时候必须用」；系统提示加硬约束 |
| 参数错 | 枚举值写错、漏必填 | 用 schema 约束 + 枚举，让服务端校验并返回可读错误 |
| 不会恢复 | 报错后原样重试 | 错误信息要可读且带修正建议；给「最多重试 N 次」的显式指令 |

## 四、平台对照：卖的不只是模型

| 平台 | 定位 | 强项 | 注意 |
| --- | --- | --- | --- |
| **阿里百炼 / DashScope** | 全栈 MaaS + Agent 平台 | Qwen 家族齐全、OpenAI 兼容、知识库与编排、与 SAA/AgentScope 原生打通 | 私有扩展能力要用原生协议 |
| **火山方舟** | 模型广场 + 推理服务 | 多厂商模型聚合、豆包系性价比、批量推理 | 各模型能力差异大，需逐个验 |
| **腾讯云（TI / ADP）** | 行业大模型平台 | 与微信/企微生态、行业方案 | 偏解决方案交付，SDK 灵活度一般 |
| **华为 ModelArts / 盘古** | 政企与私有化 | 信创适配、私有化交付 | 生态偏项目制，社区资料少 |
| **硅基流动等聚合商** | 多模型 API 聚合 | 一个 key 调多家、按量灵活 | 稳定性和 SLA 取决于上游 |

> [!NOTE] 平台选型的两条硬约束
> ① **能否私有化**——政企、金融、医疗项目往往一票否决；② **能否锁定模型版本**——很多平台默认滚到最新快照，行为会漂移，必须显式指定版本号。

## 五、价格结构：比单价更重要的是结构

不同平台计费口径差别很大，只看「每百万 token 多少钱」会算错：

| 计费维度 | 说明 | 对 Agent 的影响 |
| --- | --- | --- |
| 输入 / 输出分开计价 | 输出通常贵 2～4 倍 | Agent 输出多（含思考），成本偏向输出 |
| 上下文缓存 | 命中缓存输入大幅折扣 | 稳定的 system prompt + 长文档适合缓存 |
| 长上下文阶梯 | 超阈值后单价上升 | 塞满上下文比想象中贵 |
| 多模态按图/秒 | 与 token 无关 | 视觉 Agent 要单独算 |
| 批量推理折扣 | 离线任务可便宜数倍 | 离线索引/评测应该走批量 |
| 失败重试也计费 | 429 前的请求可能已计费 | 重试策略直接影响账单 |

一个粗略的成本拆法（详见 [可观测性：成本归因](#/engineering/observability)）：

```
月成本 ≈ Σ(每类调用次数 × (输入 token × 输入单价 + 输出 token × 输出单价))
```

先按**调用类型**拆（路由/抽取/主推理/评测），你会发现优化空间通常不在主推理。

## 六、私有化部署的代价

很多团队以为「私有化 = 把模型下下来跑起来」，实际是三件事：

| 项 | 现实 |
| --- | --- |
| 显存 | 参数量 × 精度字节 + KV Cache 余量。70B 级模型单卡装不下，多卡要算并行效率 |
| 吞吐 | 自建集群的并发能力通常远低于云厂商，要按峰值而非均值规划 |
| 运维 | 模型升级、多版本并存、灰度、监控 GPU 利用率，全是新工作量 |
| 能力落差 | 开源权重通常落后闭源旗舰一档，某些任务（长上下文、多模态）差距更大 |

**判断标准**：只有当「数据绝对不能出内网」或「调用量足够大且稳定」时，私有化才在经济上成立。前者是合规刚需，后者要算三年 TCO。

三条路径的取舍：

| 路径 | 优点 | 缺点 | 适合 |
| --- | --- | --- | --- |
| 框架自带抽象（Spring AI `ChatModel`） | 类型安全、可测试、与 Advisor 打通 | 绑定框架 | Java 项目默认选它 |
| OpenAI 兼容协议 | 换厂商只改 base_url 与 model | 私有扩展能力会被吃掉 | 多语言、轻量项目 |
| 网关（Higress） | 业务零改动、集中限流与审计 | 多一跳、需运维 | 多团队多模型 |

**迁移检查清单**（换模型时逐条过）：

1. 模型名是否锁定版本号，而不是 `latest`
2. 工具 schema 字段是否有厂商不支持的（如某些 `oneOf`、深层嵌套）
3. 是否依赖了私有参数（`enable_thinking`、`thinking_budget` 之类）——兼容模式下通常静默失效
4. `max_tokens`、温度、top_p 的默认值是否一致
5. 流式响应的分块格式与结束标记是否一致
6. 结构化输出是「原生 json_schema 约束」还是「提示词要求 + 后处理」——可靠性差一个数量级
7. 错误码映射：429 / 5xx / 内容拦截，各自的处理分支是否补齐
8. 重跑一遍那 20 条工具调用用例

## 常见坑

> [!WARNING] 六个选型误判

1. **看榜单选型**。知识问答榜单与工具调用能力相关性弱，必须用自建用例实测。
2. **用旗舰模型做路由和分类**。这类调用占比高、任务简单，成本会和效果不成正比地浪费。
3. **忽略限流配额**。RPM/TPM 打满时表现为大面积 429，看起来像「模型不稳定」，其实是容量问题。
4. **套用「上下文越长越好」**。长上下文中段信息易被忽略，且单价阶梯更贵；能检索就不要硬塞。
5. **不锁模型版本**。平台默认滚动更新，某天行为突变很难归因。
6. **在业务代码里直接 new 厂商 SDK**。换模型时改动面扩散到全仓，这是最常见的架构债。

## 自测题

> [!QUESTION] 为什么不能用公开榜单来选 Agent 用的模型？
> 榜单主要测知识问答与推理题，而 Agent 依赖的是工具调用的意图识别、参数正确性、错误恢复与多轮一致性，两者相关性很弱，必须用自己的用例实测。

> [!QUESTION] 模型、平台、部署形态三层，哪一层更换成本最高？为什么？
> 部署形态。模型只需改配置（前提是做了抽象），平台是协议与配额适配，而私有化涉及硬件、吞吐规划、模型升级与 GPU 运维，是长期投入。

> [!QUESTION] 价格结构里，哪一项最容易被漏算，对 Agent 影响最大？
> 输出侧计价（Agent 输出含思考与工具参数，通常比输入贵数倍）与失败重试的隐性计费，二者叠加会让实际成本显著高于按单价做的估算。

> [!QUESTION] 多模型抽象的三条实现路径分别适合什么情况？
> 框架自带抽象适合已选定框架的项目（类型安全、可测试）；OpenAI 兼容协议适合轻量、多语言项目（换厂商只改 base_url）；网关适合多团队多模型、需要集中限流与审计的场景。
