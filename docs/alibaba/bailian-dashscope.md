# 百炼与 DashScope：模型服务与知识库

> [!ABSTRACT] 一句话版本
> - 三个名字分工明确：**百炼**是平台（编排、知识库、配额、账单），**DashScope** 是 API（原生端点 + OpenAI 兼容端点），**Qwen** 是模型。
> - 两种端点不是等价的：**OpenAI 兼容模式方便换厂商，但私有能力（思考模式、多模态文件、缓存标记）会被吃掉**。要用全能力就走原生协议。
> - 平台知识库适合「快速搭起来」，不适合「调到极致」：切分策略与召回参数可调空间有限，复杂场景必须自建 RAG。
> - 生产必做三件事：**429 分级退避 + 模型降级**、**上下文缓存**、**按调用类型分摊成本**。

> [!NOTE] 和其他页的分工
> 本页讲**平台与 API 怎么用、边界在哪**。模型能力对比看 [国产模型与云平台对照选型](#/alibaba/domestic-stack)；RAG 的算法细节看 [检索优化](#/knowledge/retrieval-advanced)；聚合与治理（多模型统一入口）看 [Higress：AI 网关](#/alibaba/higress-gateway)。

## 一、三层职责：一句话分清楚

| 层 | 你在这里做什么 | 典型动作 |
| --- | --- | --- |
| 百炼（Model Studio） | 开通模型、配配额、搭知识库、编排应用、看账单 | 点控制台 |
| DashScope | 发请求、拿响应、处理错误 | 写代码 |
| Qwen | 实际推理 | 你只选档位与参数 |

**这层区分很重要**，因为很多问题是「层次错位」造成的：比如在代码里反复拼 prompt 想模拟知识库检索（应该在百炼建知识库或自建 RAG），或者在平台编排里做复杂分支（应该写代码）。

兼容模式里最容易掉的四样东西：

| 能力 | 兼容模式表现 | 应对 |
| --- | --- | --- |
| 思考模式（thinking） | 默认可能关闭，且无统一字段 | 用 `extra_body` 透传，或走原生 |
| 思考预算（thinking budget） | 无标准字段 | 原生协议 |
| 多模态文件上传 | 支持度不一，常需 URL 或 base64 | 原生 / 文件服务 |
| 上下文缓存标记 | 各厂商字段不同 | 原生，或依赖平台自动缓存 |

**判断方法很简单**：拿一个你以为「模型不会」的任务，先用原生协议试一次。若原生能、兼容不能，就是兼容层丢参数，不是模型能力问题。

## 三、关键参数：真正影响行为的只有几个

| 参数 | 作用 | 常见误用 |
| --- | --- | --- |
| 模型档位 | 能力与成本上限 | 全用旗舰，成本失控 |
| `temperature` | 随机性 | Agent 决策链路设太高，工具选择不稳 |
| `max_tokens` | 输出上限 | 设太小导致 JSON 被截断，解析失败 |
| 思考模式 | 是否先推理再答 | 开着做分类，白烧 token；关着做复杂规划，质量下降 |
| `stream` | 流式返回 | 后台任务用流式，白白增加处理复杂度 |
| `tools` | 工具定义 | 一次塞几十个，选择准确率下降 |
| 结构化输出 | 约束 JSON schema | 只靠提示词要求 JSON，靠正则兜底 |
| 并行工具调用 | 一次发多个调用 | 有副作用的工具并行执行，顺序错乱 |

**Agent 场景的推荐基线**：决策与工具选择用低温度（接近 0），生成类内容再调高；分类/抽取类调用关思考模式，规划类调用开；所有输出都设 `max_tokens` 上限，避免异常长输出打爆下游。

## 四、平台能力：省事与黑盒的边界

| 能力 | 能省什么 | 天花板在哪 |
| --- | --- | --- |
| 应用编排 | 可视化搭多步流程 | 复杂分支/循环表达力弱，调试粒度粗 |
| 知识库 | 上传文档即有 RAG | 切分策略、召回参数可调空间小；混合检索与重排能力有限 |
| Prompt 管理 | 版本化、灰度 | 与代码里的模板容易形成两套真相 |
| 评测 | 批量跑用例、看分数 | 裁判模型与指标自定义能力有限 |
| 配额与账单 | 分项目限额、成本可见 | 细到「按调用类型」的归因要自己做 |

### 什么时候该自建 RAG

以下任一成立，就别指望平台知识库：

1. 需要**权限过滤前置**（不同用户看到不同文档，且必须在检索前过滤而非事后删）
2. 需要**混合检索 + 重排**（关键词 + 向量，再精排）
3. 需要**父子 chunk**（小块检索、大块喂给模型）
4. 需要**引用可追溯**到页码/段落，且要校验引用真实性
5. 文档量极大或有复杂增量更新策略

具体做法见 [文档解析与切分策略](#/knowledge/document-pipeline) 与 [检索优化](#/knowledge/retrieval-advanced)。平台知识库的最佳位置是：**MVP 验证期、非核心业务、内部工具**。

## 五、配额、限流与降级

这是上线后最先撞上的墙。典型现象：平时好好的，一到高峰大面积超时，日志里一堆 429。

分层处理：

| 层 | 做法 |
| --- | --- |
| 客户端 | 指数退避 + 抖动，别用固定间隔重试 |
| 请求层 | 降低 `max_tokens`、缩短上下文、关思考模式（省 token 也省配额） |
| 模型层 | 降级：Max → Plus → Flash；复杂任务宁可排队也不要降级到答错 |
| 业务层 | 非关键调用（摘要、打标）异步化或延后 |
| 容量层 | 提前申请配额；把峰值与均值分离规划 |

> [!WARNING] 重试的反模式
> 「429 就立刻重试三次」会让情况更糟：重试请求本身也占配额，形成自我放大的拥塞。正确做法是**带抖动退避 + 熔断 + 降级**，并把「降级到了哪个模型」记进 trace。

## 六、计费：三个容易被忽略的点

1. **输入与输出分开计价，输出更贵**。Agent 的输出包含工具参数与思考内容，往往比预期长。
2. **上下文缓存有折扣，但需要「稳定的前缀」**。系统提示与长文档放在前面、变动内容放后面，命中率才高。
3. **长上下文有单价阶梯**。塞满上下文不只是慢，是按更高档计费。

一个可执行的动作：**给每类调用打标签**（`route` / `extract` / `main` / `eval`），按标签统计 token。你会发现优化空间八成不在「主推理」，而在高频小调用。归因方法见 [可观测性：成本归因](#/engineering/observability)。

## 七、内网与私有化接入

| 形态 | 适用 | 注意 |
| --- | --- | --- |
| 公网端点 | 一般业务 | 密钥走环境变量或 KMS，绝不进代码库 |
| 专有网络 / 私网接入 | 数据敏感、要求不出公网 | 需规划 VPC、路由与出网策略 |
| 专属实例 | 稳定高并发、要隔离 | 容量按峰值预留，成本固定 |
| 开源权重自建（vLLM 等） | 绝对不能出内网 | 显存、吞吐、运维全是自己的 |

从公网切到私网，最容易忘的两件事：**健康检查与超时配置**（内网链路的超时语义可能不同）、**日志里是否还在打印完整 prompt**（敏感数据会随日志流入日志平台）。

## 常见坑

> [!WARNING] 六个高频坑

1. **把兼容模式当全集**。以为模型不支持思考模式或某些多模态输入，其实是兼容层没透传参数。
2. **用旗舰模型做分类路由**。这类调用占比高、任务简单，是成本浪费的主要来源。
3. **`max_tokens` 设太小**。结构化输出被截断，表现为「模型偶尔返回半个 JSON」，极难定位。
4. **429 直接重试**。重试本身占配额，会放大拥塞；应退避 + 熔断 + 降级。
5. **把平台知识库当万能**。权限过滤、混合检索、引用溯源这三件事它通常做不深。
6. **在日志里打完整 prompt**。提示词里常含客户数据与内部信息，日志平台往往权限更宽。

## 自测题

> [!QUESTION] 百炼、DashScope、Qwen 各自的职责是什么？
> 百炼是平台层（模型开通、应用编排、知识库、评测、配额与账单），DashScope 是 API 与协议层（原生端点与 OpenAI 兼容端点），Qwen 是实际执行推理的模型。

> [!QUESTION] OpenAI 兼容模式会丢失哪些能力？怎么判断？
> 常见的是思考模式与思考预算、多模态文件上传方式、上下文缓存标记等厂商私有字段。判断方法：同一任务先用原生协议跑一次，能用而兼容模式不能用，即说明是兼容层丢参数。

> [!QUESTION] 为什么说「平台知识库适合 MVP 不适合极致优化」？
> 它的切分策略与召回参数可调空间有限，缺少权限前置过滤、混合检索与重排、父子 chunk、引用溯源校验等能力，复杂场景必须自建 RAG 流水线。

> [!QUESTION] 遇到大面积 429，正确的分层处理是什么？
> 客户端指数退避加抖动、减少单次 token 消耗、模型降级（Max→Plus→Flash）、非关键调用异步化，并提前按峰值申请配额；同时记录降级轨迹便于归因。
