# 国内合规：备案、内容安全与数据边界

> [!ABSTRACT] 一句话版本
> - 三条线同时成立才算「能上线」：**备案（主体资格）**、**内容安全（输出可控）**、**数据边界（输入合规）**。
> - **调第三方 API 不等于转移责任**：面向公众提供服务的是你，你仍是服务提供者。这一点决定了大部分工作在应用侧，不在模型侧。
> - 工程上真正要做的是四件事：**输入过滤、输出过滤、人工兜底通道、全链路审计**。这四件同时也是排障与运营的基础设施，不是纯成本。
> - 具体义务以监管要求、行业规定与你所在法务的判断为准；本页只整理**工程视角该准备什么**，不构成法律意见。

> [!NOTE] 和相邻页的分工
> 技术侧的注入防御与越权见 [安全与合规：注入、越权与数据边界](#/engineering/security-hardening)；本页聚焦**监管与流程**这一面。审计的数据结构见 [可观测性](#/engineering/observability)。

## 二、备案：先搞清楚「你是不是服务提供者」

| 情况 | 通常是否需要面向公众服务的备案 | 说明 |
| --- | --- | --- |
| 面向境内公众提供生成式 AI 服务（含免费） | 需要 | 与是否收费无关，看是否向公众提供 |
| 企业内部使用、不对外 | 通常不需要 | 但若涉及内部员工外的用户，性质会变 |
| 只是调用第三方模型 API 对外提供服务 | **仍需要** | 你是服务提供者；模型来源填第三方 |
| 开源模型自行部署对外服务 | 需要 | 语料来源与安全评估要能说清 |
| 仅做技术研究、不提供服务 | 通常不需要 | 一旦对外可访问就进入监管范围 |

**最容易误判的一条**：以为「我用的是百炼的模型，备案是阿里的事」。实际是**双层责任**——模型提供方有模型侧的合规义务，你作为应用方有服务侧的义务（内容安全、用户管理、投诉处理）。

需要准备的核心材料（具体清单以属地要求为准）：

| 项 | 要点 |
| --- | --- |
| 主体信息 | 营业执照、法人、安全责任人 |
| 模型来源 | 自研 / 开源（名称与许可证）/ 第三方 API（供应商与协议） |
| 服务形态 | 网页、App、小程序、API、插件…… |
| 面向对象 | 公众 / 特定行业用户 / 内部 |
| 安全评估 | 内容安全机制、应急处置、日志留存 |
| 语料与数据 | 来源合法性说明，是否含个人信息 |

> [!TIP] 工程侧要提前做的两件事
> ① **把「模型版本」记进配置与日志**——备案材料要写模型，事后监管问询也要能答；② **留存内容安全机制的记录**（过滤规则、拦截日志），评审时要证明「机制存在且在工作」。

两个容易忽略的义务：

- **AI 生成内容标识**：生成内容需要以适当方式标识（不同场景与载体的具体要求不同，以现行规定为准）。工程上意味着：接口返回、图片元数据、导出文件都要能带上标识。
- **投诉与更正通道**：用户要能申诉「你生成的关于我的信息是错的」。这要求你能**定位到具体一次生成**——回到审计。

## 四、数据边界：三类数据要分开对待

| 类型 | 典型内容 | 处理原则 |
| --- | --- | --- |
| 个人信息 | 姓名、手机、地址、身份证、对话中的自述 | 最小必要；能脱敏就脱敏；明确告知用途 |
| 敏感个人信息 | 生物识别、医疗健康、金融账户、行踪 | 单独同意；原则上不送第三方模型 |
| 重要/核心数据 | 行业规定范围内的数据 | 不出境、不外送，必要时本地部署 |

**给模型的内容，就是「数据出境/出域」判断的对象**。这点在 Agent 场景下更容易失守，因为上下文里会混入：检索到的文档、工具返回的结果、历史对话。三个具体动作：

1. **入口脱敏**：手机号、身份证、卡号在进模型前替换为占位符，输出后再按需回填（回填要受权限控制）。
2. **检索侧裁剪**：只把「本次任务必需」的片段放进上下文，不要整篇丢进去。
3. **工具结果白名单**：工具的返回字段要在定义里显式列出，避免 `SELECT *` 式地把整行数据塞进上下文。

## 五、审计：Agent 特有的要求

聊天机器人审计「说了什么」，Agent 还要审计「做了什么」。最小字段集：

| 字段 | 为什么必须 |
| --- | --- |
| `trace_id` / `run_id` | 把一次任务的多次调用串起来 |
| 操作人 + 租户 | 谁让它做的 |
| 工具名 + 参数（脱敏后） | 做了什么动作 |
| 目标对象 ID | 对哪条数据动的手 |
| 结果状态（成功/失败/被拦截） | 是否真的发生了副作用 |
| 审批人（若有） | 敏感操作的人工确认链 |
| 模型与提示词版本 | 事后复现与归因 |

有了这组字段，才能回答监管与客户最常问的三个问题：**谁、在什么时候、让系统做了什么。**

> [!WARNING] 审计日志本身也是敏感数据
> 参数里可能含个人信息。要么脱敏存储，要么把日志放在与生产数据同级甚至更严的权限域里。见过太多「为了合规记录一切」，结果造出一个更大泄露面的案例。

## 六、上线检查表

> [!ABSTRACT] 逐条勾选
> **备案与材料**：① 明确是否面向公众提供服务；② 模型来源与版本已记录；③ 安全评估与应急处置文档已备；④ 安全责任人已指定。
>
> **内容安全**：⑤ 输入过滤覆盖注入与违规请求；⑥ 输出过滤覆盖违法不良信息与个人信息；⑦ 检索与工具已做权限过滤（非事后删）；⑧ 生成内容标识已实现；⑨ 投诉与人工接管通道已上线并有人值守。
>
> **数据边界**：⑩ 敏感字段在入模前脱敏；⑪ 上下文只含任务必需内容；⑫ 工具返回字段白名单化；⑬ 日志留存期限与访问权限已定。
>
> **审计与可回滚**：⑭ 写操作全量留痕且可定位到人；⑮ 敏感操作有人工确认；⑯ 误操作可回滚或有补偿方案。

## 常见坑

> [!WARNING] 六个高频坑

1. **以为调 API 就转移了责任**。模型提供方与应用方是双层责任，内容安全与用户管理仍在你这侧。
2. **只做输入过滤不做输出过滤**。模型可能自己编出违规内容，也可能把检索到的他人信息原样吐出。
3. **检索权限事后过滤**。先召回再删，等于让模型「看到过」无权数据，prompt 里已经泄露。
4. **日志把完整 prompt 与参数都存下来**。审计需求变成了泄露风险，必须脱敏 + 权限隔离。
5. **没有人工接管通道**。用户无法申诉、无法转人工，既是体验问题也是合规问题。
6. **上线后才补材料**。备案与安全机制需要提前准备，事后补往往影响上线时间。

## 自测题

> [!QUESTION] 调用第三方模型 API 对外提供服务，合规责任怎么分？
> 双层责任：模型提供方承担模型侧义务，你作为服务提供者仍要承担内容安全、用户管理、投诉处理等应用侧义务，不能因为「模型不是我训的」而免责。

> [!QUESTION] 为什么内容安全要做五道闸门而不是一道？
> 单点防御必被绕过：输入侧可能漏判、模型可能被诱导、检索可能带入越权内容、输出可能是编造内容；纵深防御让每层只负责一类风险，且任一层拦截都能留下记录。

> [!QUESTION] Agent 的审计为什么比聊天机器人要求更高？
> 因为 Agent 会执行真实动作（写库、发消息、下单），审计必须回答「谁在何时让系统做了什么、结果如何、是否可回滚」，而不只是记录了哪些对话文本。

> [!QUESTION] 检索权限为什么必须在召回前过滤，而不是召回后删除？
> 召回后再删，无权内容已经进入模型上下文并可能被引用或泄露；只有检索阶段带权限谓词，才能保证模型从未「看到」越权数据。
