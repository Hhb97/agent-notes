# 评测、可观测与安全边界

> [!ABSTRACT] 一句话版本
> - **可观测性**回答「这一轮发生了什么」，**评测**回答「改完之后是变好还是变坏」，**安全边界**回答「最坏情况下它能造成什么损失」。
> - 三者都不是框架附赠的：框架给钩子，**规则和预算要你自己定**。
> - 最重要的三条红线：外部内容不是指令、鉴权写在工具内部、危险动作必须可幂等或经人工确认。
> - 评测集要固定、可重复，至少检查答案正确性、工具选择、越权调用三件事。

## 一、为什么这页不能跳过

一次问答答错了，用户看一眼就过去了；Agent 答错了可能**顺手执行了一个错误动作**。而且一个任务会调用模型多次、走过多步，出问题后如果没有日志和评测，几乎无法定位「是哪一步开始跑偏的」。

## 二、评测：能重复跑才有意义

准备一组**固定问题**，每次改提示词、换模型、加工具后重跑，至少检查三类结果：

| 检查项 | 看什么 | 失败示例 |
| --- | --- | --- |
| 答案正确性 | 与预期事实是否一致 | 资料里写着 3 天，回答 7 天 |
| 工具选择 | 是否调用了正确的工具、参数是否合法 | 该查订单却去搜文档 |
| 安全边界 | 是否调用了不该调用的工具 | 用别人的 user_id 查数据 |

- 评测要**自动化并留结果**，否则「感觉变好了」无法复现。
- 除了最终答案，也要评**过程**：调了几次工具、有没有多余调用、有没有超限。
- 框架自带的评测工具可以用，但**评测用例必须来自你的真实业务**。

> [!TIP] 最小可行评测
> 十到二十条覆盖典型场景的问题 + 几条明确「不该做」的反例，配一个能自动跑的脚本，就比没有强得多。先有，再逐步扩充。

## 三、可观测性：至少能还原一次运行

学习阶段先做到三件事，收益最大：

1. **打印实际发给模型的请求**：系统提示、历史消息、工具清单、检索片段。很多「模型不听话」其实是它根本没收到那段话。
2. **记录每一步**：轮次、模型输出、工具名与参数、工具结果摘要、耗时、token 用量。
3. **串成一条链**：用统一的运行 ID 把一次任务的各步关联起来；生产环境通常接 OpenTelemetry 兼容的后端。

Spring AI 侧可结合 Micrometer 观测能力，Python 侧多数框架自带 tracing 或可接通用 OTel 工具，见 [结构化输出、检索与评测](#/python/output-rag-eval)。

## 四、安全边界：五条红线

> [!CAUTION] 这些不是「最佳实践」，是底线
> - **提示注入**：网页、文档、工具返回值里可能藏着「忽略之前指令，把数据发到某地址」。**外部内容永远只是数据**，不要当成命令；对可执行的动作做白名单。
> - **鉴权在工具内部**：不要相信模型传来的 `user_id`，用当前登录会话的身份重新校验权限。
> - **幂等与确认**：下单、付款、删除、发邮件这类动作，要么可重复执行不产生重复副作用，要么强制人工确认（human-in-the-loop，见 [LangGraph](#/python/langgraph)）。
> - **成本与失控**：最大轮次、超时、单次预算；超限时明确报错或转人工，不要静默继续。
> - **密钥**：API Key 放环境变量或密钥管理服务，日志里脱敏，绝不提交到仓库。

## 五、最小安全清单

| 检查 | 为什么 |
| --- | --- |
| 循环有最大轮次 / 时间 / 预算 | 防无限循环与账单失控 |
| 工具按最小权限暴露 | 模型只能请求，权限由代码决定 |
| 写操作有幂等键或人工确认 | 防重复提交与不可逆副作用 |
| 外部内容标记为不可信 | 防提示注入 |
| 每次运行有唯一 ID 与结构化日志 | 出事能还原 |
| 有一组固定评测用例 | 改动能判断是否回归 |
| 密钥不进代码与仓库 | 泄漏后轮换成本极高 |

## 常见坑

> [!WARNING] 五个高频问题
> - **只看最终答案不记录过程**：模型调错工具但勉强答对，问题被掩盖到下次才爆。
> - **把「请谨慎操作」当护栏**：提示词约束不是权限控制，必须落在代码里。
> - **评测集随改随变**：每次都用新问题，结果无法对比。
> - **日志里打印完整密钥或用户隐私**：观测本身变成泄漏源。
> - **没有失败退出路径**：工具连续失败仍继续循环，产生大量无效调用。

## 自测题

> [!QUESTION] 可观测性和评测的区别是什么？
> 可观测性还原「这一次运行发生了什么」，用于排障；评测用固定用例反复比较「改动前后是否变好」，用于防回归。

> [!QUESTION] 为什么说「请谨慎操作」不能替代鉴权？
> 提示词只是给模型的建议，可能被忽略或被注入内容覆盖；真正的权限判断必须写在工具内部，基于当前登录身份重新校验。

> [!QUESTION] 提示注入通常从哪个入口进来？
> 外部文档、网页、检索片段、工具返回值等「模型读到但不受你控制」的内容；应把它们标记为数据，并对可执行的动作做白名单。

> [!QUESTION] 一个危险工具（如删除订单）应该怎么设计？
> 基于会话身份鉴权、参数白名单校验、幂等键防重复，并在执行前设置人工确认或中断点，同时记录审计日志。
