# 模型选型与关键参数

> [!ABSTRACT] 一句话版本
> - 选模型不是选「最聪明的」，而是选**与任务形态、预算、延迟、数据合规都匹配**的那一档。
> - 六个维度：推理能力、上下文长度、**工具调用 / 结构化输出支持**、延迟、成本、部署与合规。Agent 场景里第三项常被忽略却最容易翻车。
> - 参数里 `temperature` 控制随机性、`max_tokens` 控制输出上限；**不同厂商支持的参数与默认值不同**，以所用版本文档为准。
> - 最实用的成本手段是**分级路由**：简单任务走小模型，只在必要时升级。

## 一、六个选型维度

| 维度 | 要问什么 | 忽略后果 |
| --- | --- | --- |
| 推理能力 | 任务是分类/抽取，还是多步推理与规划？ | 简单任务用贵模型，或复杂任务用小模型反复失败 |
| 上下文长度 | 系统提示 + 工具清单 + 历史 + 检索片段有多大？ | 装配时被截断，关键约束丢失 |
| **工具调用 / 结构化输出** | 是否稳定支持工具调用、schema 约束、并行调用？ | Agent 循环频繁失败、参数幻觉 |
| 延迟 | 同步接口的 P95 要求是多少？ | 长任务阻塞网关 |
| 成本 | 单次任务的 token 预算是多少？ | 账单随轮次放大 |
| 部署与合规 | 数据能否出域？是否需要私有化 / 特定区域？ | 方案直接不可用 |

> [!TIP] Agent 场景的硬门槛
> 一个模型再会聊天，如果**工具调用不稳定**（漏调、参数乱编、不支持并行调用结果对齐），就不适合做 Agent 主模型。选型时先用几轮真实工具调用压测，而不是只看通用榜单。

## 二、常见参数

| 参数 | 作用 | 建议 | 注意 |
| --- | --- | --- | --- |
| `temperature` | 采样随机性，越低越确定 | 工具调用、抽取、分类调低；创作用高一点 | **不是「聪明程度」旋钮** |
| `top_p` | 候选 token 的累积概率范围 | 一般与 temperature 二选一调整 | 两个一起大幅改动难以归因 |
| `max_tokens` | 单次输出上限 | 与预算、超时一起设；为输出预留额度 | 太小会被截断，太大浪费预算 |
| `stop` / 结束序列 | 指定停止生成的标记 | 结构化输出、批量任务有用 | 不同厂商叫法不同 |
| `seed` | 尽量复现同样输出 | 评测与回归时有用 | 通常是「尽力而为」，不保证完全一致 |
| 响应格式约束 | 要求 JSON / 指定 schema | 优先用框架的结构化输出能力 | 见 [结构化输出与护栏](#/llm/structured-output-guardrails) |
| 工具调用相关配置 | 是否允许并行、是否强制调用某工具 | 按任务选择 | 写操作并行要串行化或幂等 |

> [!NOTE] 参数不是跨厂商通用
> 上表是**概念**。具体参数名、取值范围、默认值、是否支持，各家模型服务与 SDK 版本都不同；照抄别人的配置前先查对应文档。

## 三、分级路由怎么落地

| 步骤 | 做法 |
| --- | --- |
| ① 入口分类 | 用规则或最便宜模型判断任务类型：闲聊 / 简单查询 / 复杂推理 / 越权请求 |
| ② 选择档位 | 简单任务小模型，复杂任务升级；越权请求直接拒答不进模型 |
| ③ 失败升级 | 小模型输出不合格（校验失败 / 工具调用失败）时，有限次升级重试 |
| ④ 统一治理 | 无论哪一档，都经过同一套预算、超时、降级与观测，见 [生产级 Agent 架构全景](#/deep/agent-architecture) |
| ⑤ 归因评测 | 分档位统计正确率、延迟、成本，验证路由规则是否划算 |

> [!WARNING] 别让路由变成新的复杂度
> 如果只有一个任务类型、流量也不大，先固定一个模型档位；等成本或延迟成为真实瓶颈，再引入路由与失败升级。

## 四、评测驱动的选型

选型结论必须来自**自己的用例集**，而不是通用榜单：

| 指标 | 说明 |
| --- | --- |
| 任务正确率 | 用业务用例集测，含边界与反例 |
| 工具调用成功率 | 选对工具、参数合法、结果对齐 |
| 结构化输出合规率 | schema 校验通过比例 |
| P50 / P95 延迟 | 区分同步与长任务 |
| 单次成本 | 平均 token 与费用，含失败重试 |
| 越权 / 危险动作 | 必须为零，一票否决 |

## 常见坑

1. **只看通用榜单**：不看工具调用稳定性，Agent 上线后频繁失败。
2. **温度调高期待「更聪明」**：只会更随机，工具参数更容易漂移。
3. **同时改多个参数**：无法归因，评测失去意义。
4. **不给输出预留额度**：长回答被截断，下游解析失败。
5. **换模型不重跑用例集**：提示词与工具描述往往要跟着调整。
6. **忽略合规与数据出域**：技术方案再好也可能不可用。

## 自测题

> [!QUESTION] Agent 场景选模型时最容易被忽略的维度是什么？
> 工具调用与结构化输出的稳定性（是否漏调、参数是否合法、并行结果能否对齐）；它直接决定循环能否可靠跑完。

> [!QUESTION] temperature 调高会让模型更聪明吗？
> 不会。它提高采样随机性，适合创作；在工具调用和抽取任务里反而会增加参数漂移与格式不稳定。

> [!QUESTION] 分级路由为什么能降低成本？
> 大量请求其实是闲聊、简单分类或查询，用便宜档位即可；只在校验失败或判定为复杂任务时升级，把贵模型的用量集中在必要处。

> [!QUESTION] 为什么选型结论必须来自自己的用例集？
> 通用榜单不反映你的提示词、工具 schema、领域术语与权限约束；只有用业务用例集测正确率、工具成功率、延迟与成本，结论才成立。
