# 评测系统深入：数据集、裁判与指标漂移

> [!ABSTRACT] 一句话版本
> - 评测系统分五层：**数据集 → 执行器 → 裁判 → 指标 → 门禁**；缺任何一层，「改完感觉变好了」就无法证伪。
> - 数据集要**分层**：典型正例、边界例、安全反例、故障例、线上回流坏例，并版本化、脱敏。
> - 三类裁判各有偏差：规则裁判稳定但覆盖窄、模型裁判便宜但会**偏袒长答案 / 自家模型**、人工最可信但慢；要用校准集量化裁判本身的质量。
> - 指标要看**过程与安全**，并用置信区间 / 显著性判断差异是否真实；线上分布变化会带来**指标漂移**，需持续监测。

## 二、数据集构建

| 层 | 占比参考 | 作用 |
| --- | --- | --- |
| 典型正例 | 50% | 衡量主干能力 |
| 边界例 | 20% | 歧义、资料不足、多轮指代、超长输入 |
| **安全反例** | 15% | 越权、危险动作、注入文本、隐私请求 |
| 故障例 | 10% | 工具超时、检索为空、模型限流 |
| 回流坏例 | 5% 起（持续增长） | 线上真实失败，防止旧问题复发 |

| 要求 | 说明 |
| --- | --- |
| 分层抽样 | 按业务场景 / 用户类型 / 难度分层，避免数据集只覆盖高频简单场景 |
| 标注规范 | 明确「什么算正确」，含可接受的多答案与拒答标准 |
| 标注一致性 | 多人标注同一批，计算一致率；分歧样例要复议 |
| 脱敏 | 去掉个人信息与内部敏感数据，保留语义 |
| 版本化 | 数据集改动本身要能回溯，否则跨版本指标不可比 |
| 防泄漏 | 提示词调优不能「背下」评测答案；保留一份不公开的留出集 |

> [!WARNING] 数据集被提示词「记住」是隐形失效
> 反复用同一批用例调提示词，等于在测试集上训练。保留一份**从未参与调优的留出集**，定期用它验证真实泛化能力。

## 三、三类裁判

| 裁判 | 适合 | 主要偏差 | 对策 |
| --- | --- | --- | --- |
| **规则 / 程序断言** | 工具选择、schema 合规、越权、危险语句 | 覆盖窄，语义判断无能 | 能规则化的绝不交给模型 |
| **LLM-as-judge** | 答案相关性、完整性、语气 | 偏袒长答案、偏袒同族模型、位置偏差、打分不稳定 | 固定裁判模型与提示词、交换输出顺序、给评分锚点、抽样人工校准 |
| **人工** | 主观质量、争议样例、安全边界 | 慢、贵、标注者主观差异 | 标注规范 + 一致性检验 + 争议复议 |

**裁判本身要被评测**：准备一小批人工标注的校准集，定期计算模型裁判与人工的一致率；一致率下降说明裁判提示词或模型版本出了问题，此时「指标变好」可能是裁判漂移而非系统变好。

## 四、指标体系

| 类 | 指标 |
| --- | --- |
| 质量 | 答案正确率、依据可追溯率、拒答正确率、完整性 |
| 过程 | 工具选择准确率、调用轮次、多余调用率、回填正确率 |
| 安全 | 越权调用数、未审批写操作数、危险语句拦截率、注入成功率（**一票否决**） |
| 成本效率 | 平均 / P95 token、单次成本、P50 / P95 延迟、重试率 |
| 稳定性 | 同输入多次运行的一致率、超时率、降级触发率 |

**统计判断**：样本少时正确率的几个百分点可能只是噪声。给出置信区间，或用固定随机种子做配对比较；A/B 结论要有显著性依据，别凭一次跑分定胜负。

## 五、指标漂移

| 漂移来源 | 表现 | 监测 |
| --- | --- | --- |
| 线上数据分布变化 | 离线指标好、线上投诉多 | 线上抽检分布 vs 数据集分布对比 |
| 模型版本更新 | 同一用例集分数跳变 | 锁定模型版本，更新时强制全量评测 |
| 提示词 / 工具 schema 变更 | 过程指标先变、质量指标后变 | 每次变更记录版本并重跑 |
| 裁判模型漂移 | 分数变化但系统没改 | 校准集一致率监控 |
| 检索索引更新 | Recall 变化 | 检索指标单独看，见 [检索优化](#/knowledge/retrieval-advanced) |

> [!TIP] 先分层归因再谈提升
> Recall 低是检索问题、工具选错是 schema / 描述问题、答案错但依据齐是生成问题。把所有指标压成一个总分，就失去了定位能力，见 [测试策略](#/engineering/testing)。

## 六、门禁规则示例

```text
发布条件：
  1. 安全类指标全部为 0 例外（一票否决）
  2. 质量类指标不低于基线（允许 ±噪声范围内的波动）
  3. 成本 / P95 延迟不超过基线 + 阈值
  4. 留出集单独跑，不参与调优
  5. 全量逐例结果可 diff：新增失败用例必须逐条解释
  6. 灰度期线上抽检继续监控，异常自动回滚
```

## 常见坑

1. **只评最终答案**：过程回归（选错工具、多轮循环）全漏掉。
2. **裁判模型与被测模型同族且不校准**：分数系统性偏高。
3. **数据集不分层 / 无反例**：安全边界无人验证。
4. **在测试集上反复调提示词**：指标虚高，线上泛化差。
5. **忽略置信区间**：把噪声当成提升或回归。
6. **不保存逐例结果**：只知道「平均分降了」，不知道哪几条坏了。

## 深入追问

> [!QUESTION] 为什么要保留不参与调优的留出集？
> 反复用同一批用例调提示词等于在测试集上训练，指标会虚高；留出集用来验证真实泛化能力。

> [!QUESTION] LLM-as-judge 有哪些典型偏差，怎么缓解？
> 偏袒长答案、偏袒同族模型、位置偏差、打分不稳定；用固定裁判版本、交换输出顺序、评分锚点与人工校准集来量化并缓解。

> [!QUESTION] 为什么指标要分层而不是压成一个总分？
> 检索、工具、生成、安全各自会独立退化；分层指标才能定位瓶颈，单总分只能告诉你「变差了」却不知道哪里。

> [!QUESTION] 分数变好但系统没改动，可能是什么问题？
> 裁判模型或提示词漂移、线上/离线数据分布变化、检索索引更新等；用校准集一致率与分布监控区分「系统变好」和「尺子变了」。
